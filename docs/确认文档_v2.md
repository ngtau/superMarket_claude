## 二、需要你确认的事项（已按建议执行，逐条说明理由与回退成本）

### §2.1 数据库：我不替你选云厂商，但把「本地一键起库」补齐了 ★ 建议接受

- **已执行**：新增根目录 `docker-compose.yml`（Postgres 16，含 healthcheck、数据卷、固定端口 5432），并在根 `package.json` 暴露 `db:migrate` / `db:seed` / `db:seed:demo`。
- **理由**：选云厂商是业务决策（计费、区域、备份策略、是否需要 PITR），不该由我替你定。但无论选哪家，本地都要有一个可丢弃的库做联调与跑 E2E，这是确定需求，先补齐。
- **仍待你定**：Neon / Supabase / RDS 三选一。注意 D1 的坑——**Neon direct 端点 + 客户端池，或 pooled 端点 + 去掉客户端池，二选一，不要双重池化**。
- **回退成本**：零，`docker-compose.yml` 是新增文件，删掉即回到原状。

### §2.2 vike PDP SSR/ISR：决策不做 ★ 建议接受

- **决策**：本轮不引入 vike，改用「动态 sitemap 脚本 + 静态 OG + PDP JSON-LD」过渡。
- **理由**：
  1. vike 会把前端从 Vite SPA 迁到 SSR 框架，涉及路由、数据获取、部署形态（Node 常驻进程 vs 静态托管）三处改动，**是当前阶段改动面最大的一项**；
  2. 收益端只有 SEO：PDP 是 SPA 时，不执行 JS 的爬虫看不到商品正文。但 Google 爬虫执行 JS，且本项目已提供 sitemap + structured data，覆盖面已可接受；
  3. 排在「真实数据库 + E2E + 支付商户号」之后——后者不上线就没有流量，SEO 优化没有意义。
- **已执行的替代方案**：`packages/server/src/scripts/generate-sitemap.ts`，从库里生成全量 PDP / 分类 / 静态页的 `sitemap.xml`，可挂定时任务或发布流程；PDP 已输出 Product JSON-LD。
- **回退成本**：低（sitemap 脚本独立），将来上 SSR 也不冲突。

### §2.3 批量导入导出：维持 CSV，不做 xlsx ★ 建议接受

- **决策**：不做 xlsx。
- **理由**：xlsx 需新增 `exceljs`（约 1MB 依赖 + 一套完全不同的读写路径），而当前使用者是后台运营，CSV 用 Excel 打开无差异；且 CSV 已实现**整批校验、任一行失败整批回滚**，语义正确性比文件格式重要得多。
- **回退成本**：低，需要时按同一 service 接口加一个 xlsx 分支即可。

### §2.4 Zod 校验：只补了商品新增，其余按模块推进 ★ 建议接受

- **已执行**：`POST /admin/products` 接入 `productCreateSchema`（shared 层），非法入参在接口层返回字段级 400，不再一路走到 Drizzle 炸 500。
- **理由**：不做「一次全补」。原因是其余 admin 端点（折扣、运费模板、角色权限等）的 DTO 形状需要与前端表单逐字段对齐，批量补容易引入「校验比实际表单更严」的假失败；逐个模块补，每补一个就能联调验证一个。
- **待补优先级**：marketing（折扣/满减，金额与门槛是数值错误高发区）→ shipping（运费模板）→ roles/admins（权限分配）。
- **风险提示**：这不构成安全漏洞——Drizzle 参数化查询 + RBAC 已挡住越权与注入，未补模块的风险只是「错误提示不友好」。

### §2.5 E2E 中后台动作走 API 而非 UI ★ 建议接受

- **决策**：`admin-fulfillment.spec.ts` 中「审核付款 / 发货」两步走 HTTP API，仅最后一步「买家确认收货」走 UI。
- **理由**：后台在 `admin.*` 独立 host（`src/lib/host.ts` 的 `isAdminHost` 判定），本地 `127.0.0.1` 与 CI 的 `ubuntu-latest` 都拿不到该域名，走 UI 需要改 hosts 或额外解析，维护成本高于收益；而这两步的业务逻辑（支付状态机、订单状态机）由 API 调用同样能完整覆盖。
- **回退成本**：低，将来若搭了 admin 域名，把这两步换成页面操作即可。

### §2.6 演示数据脚本独立为 `db:seed:demo` ★ 建议接受

- **决策**：新增 `pnpm db:seed:demo`，与系统必需数据（`db:seed`）分离。
- **理由**：`db:seed` 写的是角色/权限/D20 默认值/初始超管，**任何环境都必须跑**；演示商品**生产环境绝不能跑**。拆开后生产部署流程只需执行 `db:seed`，从流程上杜绝误把假商品塞进真实库。
- **E2E 依赖**：用例通过固定商品名「自動化測試商品（勿刪）」定位 fixture，避免依赖「列表第一条」这类不稳定假设；脚本按 `nameZh` 幂等，可重复执行。
- **回退成本**：零。

### §2.7 `packageManager` 从 `pnpm@11.11.0` 改为 `pnpm@9.15.9` ★ 建议接受（一致性修复）

- **问题**：根 `package.json` 声明 `pnpm@11.11.0`，但 lockfile 是 `lockfileVersion: '9.0'`（pnpm 9 生成），实际开发环境用的也是 9.15.9。CI 里 corepack 会按 `packageManager` 拉 pnpm 11，与 lockfile 大版本不一致时可能触发非预期升级或 install 失败。
- **决策**：以 lockfile 为准，回写 9.15.9。
- **回退成本**：若你想升 pnpm 11，需重新生成 lockfile（会是一次大 diff），建议单独排期。

### §2.8 支付超时范围：沿用 v1 决策（只作用于 `pending`）★ 已执行

银行转账凭证已上传待人工审核时（`pending_review`）不参与超时置失败——审核耗时不可控（跨天/非工作日），一并超时会误杀正常订单。若你要严格按 D20④ 执行，改 `scheduler.service.ts` 里一行 `where` 即可。

### 本轮 E2E 照出的三个真实缺陷（已全部修复）

这正是"E2E 的价值远高于单测"的实际例证——三个问题单测都覆盖不到，且都是**用户可见的功能断裂**：

| # | 问题 | 影响 | 修复 |
|---|---|---|---|
| 1 | **商品详情页「加入購物車」只写本地 store，从不调用服务端** | 点加购提示「已加入購物車 ✓」、Header 角标也显示 1，但**购物车页是空的**——整条购物链路实际是断的（购物车页/结算页读的是服务端） | `ProductDetailPage`：已登录 → `POST /cart/items` + invalidate `["cart"]`；未登录才落本地 |
| 2 | `uploadVoucher` 只改 `payments.status`，**不同步 `orders.paymentStatus`** | 后台审核队列能看到待审单，但**用户订单列表/详情仍显示「待付款」**，后台按支付状态也筛不出来 | `payments.service.ts`：事务内同步 `orders.paymentStatus = pending_review`（订单 `status` 保持 `pending_payment`，因订单状态机没有 `pending_review` 这一档） |
| 3 | `reject`（驳回）同样没同步回订单 | 驳回后用户端看不到结果，不知道要重新上传凭证 | `payments.admin.service.ts`：事务内同步 `orders.paymentStatus = failed` |

顺带补齐的两处一致性问题（与缺陷 1 同源）：

- **Header 购物车角标**改读服务端（`["cart"]` query，与购物车页共享缓存），否则加购后角标不动；未登录才读本地 store。
- **注册页补 `/cart/merge`**：此前只有登录页会合并游客车，注册前加购的商品在注册后凭空消失；合并后清空本地车，避免下次被重复合并导致数量翻倍。

缺陷 1 是最严重的一个——它属于"看起来完全正常、实际数据没落库"，只有真的点一遍才会暴露。

## 五、遗留风险与下一步

1. **P0 仍未闭环的只有环境**：数据库选型、域名、PSP 商户号、Resend 账号。代码层面已具备上线条件。
2. **E2E 首跑可能暴露真实缺陷**：本次用例是首次对「库存预留 → 下单 → 支付状态机 → 发货 → 收货」做端到端串联，这类串联第一次跑往往能照出单测覆盖不到的问题（例如事务边界、状态机跳步）。建议 CI 首次运行后优先看报告。
3. **Zod 覆盖不完整**（§2.4）：marketing / shipping / roles 三个模块的 admin 端点仍是 `body: any`。
4. **`sort=sales` 仍是创建时间兜底**：商品量大后排序结果会与直觉不符，需要物化视图或定期聚合表。
5. **备份导出落在本地磁盘**：当前写 `packages/server/uploads/`，生产环境需改为对象存储（S3/R2），否则容器重建即丢失，备份形同虚设。
